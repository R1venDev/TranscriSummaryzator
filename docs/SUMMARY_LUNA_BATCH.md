# Summary-only Luna Batch: архитектура и эксплуатация

Состояние документа: 2026-09-28. Opt-in summary-only backend использует Luna для полного черновика. Новая кандидатная policy `claude_opus_5_5_partitioned_audit_v3` проверяет три закреплённые части стенограммы через OpenRouter Batch `anthropic/claude-opus-5.5:batch`; пока она проверена только локальными тестами. Старые v1/v2 policy и их результаты сохранены. Ранее выполненные Gemini-прогоны и их закреплённые policy описаны ниже как история. В `config.example.json` остаётся `summary_backend: legacy_local`; новый маршрут не означает включения в речевой production release.

## Текущий кандидат: Claude Opus 5.5 по закреплённым частям источника

Новый summary-job создаёт один черновик Luna. Основные диапазоны исходных реплик покрывают стенограмму ровно один раз, с небольшим соседним контекстом на границах. Три последовательных Opus Batch item получают каждый свой исходный диапазон и **полный неизменный черновик**. Модель обязана указать исходную цитату и, заявляя `covered`, точную цитату из конкретного элемента черновика. Локальный валидатор проверяет границы, структуру, цитаты, адреса и применимость правок; он не объявляет смысл доказанным по совпадению ID. Все правки относятся к исходному черновику, несовместимые правки одного элемента удерживаются как нерешённые. Неполная стадия или неразрешённое противоречие сохраняется в качестве и видимой пометке опубликованного результата. Три отдельных Batch job позволяют штатному scheduler восстанавливаться по remote ID и учитывать каждую генерацию в общем бюджете; Batch-кэш между ними не гарантирован.

Промпт [audit v3](../summary/opus_v1/prompt_audit_v3.md) сохраняет универсальную сверку действия, роли, статуса, условия, альтернативы, чисел и поздних поправок. Он отделяет инструкции от реплик/черновика, располагает длинный источник перед завершающим заданием, требует дословных опор и завершения всех исходных окон. После реального v2 ответа с пустым `coverage` новый профиль использует `low` effort и лимит 7 000 токенов, общий для адаптивного thinking и JSON. Схема задаёт поддерживаемый `minItems: 1`, а локальный валидатор всё равно требует точное число окон и проверяет цитаты; ни JSON-форма, ни перечень риск-якорей не доказывают смысловой полноты. Выбор профиля следует [рекомендациям Anthropic для Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5) и [ограничениям structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs); реальное качество `low` нужно измерить отдельно. OpenRouter предупреждает, что [strict-схемы](https://openrouter.ai/docs/guides/features/structured-outputs) могут исполняться по-разному на разных endpoints. v2 промпт, схема и профиль остаются закреплёнными для прежних run manifests.

Первый реальный v2 сегмент завершился у провайдера штатно, но вернул `coverage=[]`, `findings=[]`, `patches=[]` вместо четырёх окон. Из 4 940 выходных токенов 4 877 пришлись на reasoning; стоимость была $0.113642. Локальная проверка отвергла этот отчёт, следующие два сегмента не отправлялись, исходный черновик остался опубликован с `coverage_incomplete`. Этот исход указывает на провал конкретного профиля и формы ответа; он не доказывает предел Opus. v3 не восстанавливает отчёт из пустого JSON и не запускает автоматический платный повтор.

### Сохранённый маршрут Opus v1

В v1 один Opus Batch item получал всю доступную стенограмму с speaker/source IDs и черновик; при предложенных правках второй item адресно проверял исправленный документ. Локальный код проверял форму, координаты и применимость правок. Полный реальный прогон завершился тремя генерациями вместе с Luna writer и стоил $0.23279075; исходниковая сверка обнаружила оставшиеся пропуски условий и поздней поправки, а также усиленный статус задачи. Изолированный результат помечен `coverage_incomplete` и не включён в речевой production. Его raw, usage и отчёт остаются в приватной истории. Старые root manifests сохраняют закреплённую v1 policy; новые v2 jobs получают иную semantic identity и не переиспользуют эти ответы как будто они прошли v2.

Сохранённый OpenRouter judge-ключ используется с прежним credential ID/version; менять секрет из-за смены модели не нужно. Перед платной отправкой backend отдельно проверяет, что ключ допускает `anthropic/claude-opus-5.5:batch`, Anthropic Batch endpoint, workspace, тариф, контекст и денежный резерв. Batch-поставку фиксируют с `provider.only: ["anthropic"]`, без скрытого fallback. Пользователь разрешил OpenRouter Batch хранить вход и результат до 30 дней без `provider.zdr`; это не сквозной ZDR. Для нового Opus-маршрута пользователь также выбрал **Workspace Input & Output Logging ON** в каждом фактически используемом workspace writer и judge: OpenRouter сохраняет полный текст входов и ответов в отдельных логах **минимум три месяца, возможно дольше**. 30 дней относятся к Batch-артефактам и не ограничивают срок хранения этих логов. Оба режима записаны в root/stage manifests и semantic identity; inference-key API не показывает состояние переключателя, поэтому оператор сверяет переключатель и фильтры Included/Excluded API Keys в каждом workspace перед приватной отправкой. [Условия I/O Logging](https://openrouter.ai/docs/guides/features/input-output-logging), [Data Collection](https://openrouter.ai/docs/guides/privacy/data-collection), [Batch-контракт OpenRouter](https://openrouter.ai/docs/batch-quickstart). Явный provider prompt cache не запрашивается, возможный cache hit не вычитается из предварительного резерва. Opus policy ограничивает резерв одного физического этапа $0.45 и всей цепочки одной встречи $0.60 при общем скользящем лимите приложения $1.00 за семь дней; фактическая цена может быть ниже резерва. Каждый Batch item считается отдельной оплачиваемой генерацией в общем ledger. [Карточка Opus Batch](https://openrouter.ai/anthropic/claude-opus-5.5:batch), [рекомендации Claude по промптам](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices).

## Сохранённая история Gemini и ограничения результатов

### Ранее выполненные полные прогоны и границы их результатов

На одной полной стенограмме состоялись два OpenRouter Batch item: Luna writer и Gemini audit. `verify` не отправлялся, поскольку Gemini вернул ноль находок и патчей. Writer израсходовал 25 900 входных и 10 420 выходных токенов ($0.003900); Gemini — 41 526 входных и 2 811 выходных ($0.020842875). Итого 80 657 токенов и $0.024742875 по фактическим usage; ledger округлил сумму до $0.024743. Оба item получили terminal status и были удалены после сохранения raw/status/usage. Дубликатов платных отправок при восстановлении не было.

Writer вернул parseable документ с ошибочной ссылкой на источник у незаполненного необязательного поля задачи. Gemini сообщил полное покрытие своих 12 окон, но не выявил этот дефект и несколько существенных смысловых ошибок. Инженерская сверка с исходной стенограммой исправила назначение и разделение действий, восполнила пропущенные рабочие детали и позднюю поправку; исходный черновик, отчёт аудитора и промежуточные версии исправлений сохранены в приватной истории. Опубликованный документ прошёл локальную структурную и источниковую проверку, содержит восемь разделов и 12 карточек, включая неназначенную. Повторной модельной проверки исправленного документа и систематического подтверждения полноты всей встречи не было. Показатель «12 окон покрыто» описывает отчёт аудитора, а не точность содержания.

Для будущих запусков [`engine.py`](../summary/luna_v1/engine.py) выполняет только узкую нормализацию: удаляет известную ссылку вне `task.source_ids` из `field_sources` незаполненного необязательного поля, сохраняет исходный raw и отдельный sidecar с изменением. Неизвестные ссылки, заполненные поля и смысл задачи этот механизм не переписывает. Ошибка в остальных полях по-прежнему остаётся ошибкой валидации. Это устраняет конкретную механическую причину отказа черновика, но не исправляет пропуски и подмены, пропущенные Gemini. Текущий опубликованный документ получен проверенным offline-восстановлением из уже оплаченных ответов без нового API-вызова; будущие прогоны должны отдельно подтвердить качество автоматического маршрута.

Затем прежний контракт [Gemini audit v2](../summary/gemini_v1/prompt_audit_v2.md) прошёл отдельный полный серверный прогон. Luna использовала 25 900 входных и 11 698 выходных токенов, Gemini — 42 457 входных и 7 766 выходных; всего 87 821 токен и $0.034702125 по фактическому provider usage. Gemini вернул один адресный патч исполнителя; условный `verify` не был отправлен, потому что консервативный резерв превысил предел $0.10 для логической пересборки. Источниковая инженерная сверка выявила существенные пропуски и неверное покрытие, не устранённые этим патчем. Результат v2 — свидетельство ограничений именно той проверки, а не доказательство невозможности Gemini заметить эти смыслы при другой организации входа. Первичные ответы и подробный разбор остаются в приватной продолжаемой истории. Уже отправленные v1/v2 jobs используют свои закреплённые prompt/schema/policy, а не новый маршрут.

Первый полный запуск прежней сегментной policy `gemini_openrouter_segment_review_v1` не дал завершённого результата: ответ Gemini на первой части был обрезан при лимите 10 000 выходных токенов. Этот сбой не является оценкой качества полного конспекта. Raw и статус попытки относятся только к той закреплённой policy.

Следующий полный r6 прогон compact v2 тоже не дал принятого результата. Luna сохранила raw и черновик, но root перешёл в `failed_validation` из-за известной ссылки на реплику, отсутствовавшей в `task.source_ids`. Первый Gemini item вернул HTTP 200 с `finish_reason=length/MAX_TOKENS` при лимите 6 500; неполный JSON не прошёл валидацию. Вторая и третья части не отправлялись, прежний принятый указатель не менялся. Порядок «сначала источник» в prompt не защищает сам по себе от обрезания ответа или смысловых пропусков; покрытия всей встречи и результата v3 этот прогон не подтверждает.

## Сохранённая политика Gemini: упакованная проверка частей v3 с полным черновиком

Следующий раздел фиксирует сохранённый Gemini-контракт и его тогдашние настройки. Упоминания «новых» заданий в этом разделе относятся к заданиям, созданным под этой policy; текущая policy Opus описана выше.

После writer-вызова Luna root manifest закрепляет `quality_policy_version: gemini_openrouter_segment_review_v3_packed`, judge workspace, модель, версии сегментации, выходные лимиты и SHA prompts/schemas. Старые незавершённые Luna/Gemini jobs, включая сегментные v1/v2, продолжают прежний контракт по своему сохранённому manifest; новый код не отправляет их повторно. Из канонической стенограммы host составляет две связные части, при длине её проекции свыше 60 000 символов — три. Каждая реплика входит в primary-диапазон ровно один раз; до четырёх соседних реплик по сторонам границы явно помечены как контекст. Границы учитывают паузы и короткие ответы, но не выдаются за безошибочное смысловое разбиение. [План и валидатор](../summary/gemini_v1/inventory_contract.py) сверяют точные source IDs, порядок и bytes реплик с исходником до dispatch.

Для каждой части отдельный Batch item получает [упакованный prompt v3](../summary/gemini_v1/segment_review_prompt_v3.md), её основные реплики с контекстом границ, **полный исходный черновик Luna** и список относящихся к части элементов черновика. В одном ответе Gemini сначала перечисляет существенные смыслы основных реплик и отмечает покрытие окон, затем оценивает каждый item относительно полного черновика. В v3 source item и его оценка находятся **в одной строке с короткими ключами**; отдельного `item_assessments` нет. `draft_assessments` содержит только элементы со статусом `partial`, `unsupported` или `uncertain`. Отсутствующий в нём элемент означает **unassessed в возвращённом отчёте**, а не `supported` или проверенную истину. Отчёт содержит находки и минимальные правки целых элементов `luna_summary_v1`, если они безопасны. [Контракт](../summary/gemini_v1/segment_review_contract.py) разворачивает упакованные строки без добавления фактов и локально проверяет полноту source-item оценок, ссылки, связи и форму патчей; ссылки доказывают координаты, но не подтверждают смысл. Отсутствие надёжной правки остаётся `unresolved`.

Части отправляются **последовательно**: следующая ждёт terminal предыдущей. При известном полном счёте её денежный резерв заменяется фактическим `usage.cost` до расчёта резерва следующей; при неизвестном счёте резерв остаётся занятым. Ответы сверяются с одним закреплённым черновиком; host откладывает конфликтующие правки одного элемента и сохраняет находки видимыми. После всех частей безопасные правки применяются к черновику один раз. Если они были, возможен один адресный `verify` по изменённым местам и связанным источникам. Прежний маршрут v4 с [source-only перечнем](../summary/gemini_v1/inventory_prompt_v1.md) частей и отдельной [глобальной сверкой](../summary/gemini_v1/prompt_reconcile_v1.md) сохранён только для уже начатых jobs с закреплённой прежней policy; новые jobs его не используют.

Для terminal `failed_validation` с сохранённым и оплаченным writer-ответом предусмотрено продолжение `python3 scripts/luna_summary_worker.py resume-saved-draft --private-root "$PRIVATE_ROOT" --prior-job-id "$PRIOR_JOB_ID"`. Оно сверяет прежний manifest, request, remote ID, raw-черновик и SHA источника, узко нормализует известную принадлежность ссылок к `task.source_ids` и повторно валидирует документ. Новый root закрепляет v3 и provenance; Luna повторно не вызывается, а Gemini отправляет штатный scheduler после подготовки. Прежний job и его raw остаются. Продолжение использует **ту же billing group**: стоимость writer и уже отправленных quality items, неизвестные резервы и число dispatch учитываются в общем лимите $0.10 и пределе шести отправок. Команда не обходит лимит и не разрешает параллельное продолжение той же группы.

Judge-ключи OpenRouter отделены от writer-ключей по роли в том же зашифрованном server-side store и в `/summary-settings`. Бесплатный `GET /api/v1/key` проверяет inference-ключ и его workspace/лимит, но сам не подтверждает доступ к Batch или account privacy policy. Перед новой отправкой worker сверяет каталог моделей для ключа, карточку `google/gemini-3.7-flash:batch` и Google Vertex endpoint, необходимые параметры, вместимость, текущие цены и общий бюджет. Для этого маршрута не требуется подтверждение Google project или paid tier: прямой Google API и `countTokens` не вызываются. Реальный ключ вводится только в защищённом UI, не в чат, код или журнал. [Контракт ключа](https://openrouter.ai/docs/api/api-reference/api-keys/get-current-key), [карточка Batch-модели](https://openrouter.ai/google/gemini-3.7-flash:batch).

Пользователь разрешил для этого маршрута OpenRouter Batch с хранением входов и результатов у шлюза **до 30 дней** и без запроса `provider.zdr`. Batch отправляется в `POST /api/v1/batches` с `endpoint: /v1/chat/completions`, моделью `google/gemini-3.7-flash:batch` и `provider.only: ["google-vertex"]`; при недоступности выбранного провайдера нет скрытого перехода к другому. Запрос содержит только текст и строгую JSON schema, без tools, audio, файлов и web search. Worker сохраняет intent и денежный резерв до POST, затем remote Batch ID после `202`. Scheduler читает только ID собственных jobs, сохраняет terminal/raw/usage и удаляет свой terminal Batch; ответ удаления содержит статус очистки OpenRouter и upstream. Неизвестный исход POST автоматически не повторяется. [Batch API Quickstart](https://openrouter.ai/docs/batch-quickstart).

На момент сверки [карточка OpenRouter Batch](https://openrouter.ai/google/gemini-3.7-flash:batch) показывает $0.375/млн входных и $1.875/млн выходных токенов; перед каждым POST используются живые цены модели и Google Vertex endpoint, включая максимумы из pricing overrides. Для вместимости применяется отдельная оценка по UTF-8 размеру полного Chat-запроса. Денежный резерв оценивает вход как максимум числа Unicode-символов и ¾ числа UTF-8 байтов плюс 2048 токенов обвязки, полный `max_completion_tokens` (7 500 для каждой проверки части v3, 3 000 для адресного `verify`), возможную цену записи кэша и запас 20%. Допуск сверяет резерв с общим $1/скользящие семь суток, а для обычной группы также с $0.10/логическую пересборку; адресно разрешённое продолжение использует динамический предел, описанный ниже. Это оценка, а не точный `countTokens` и не строгая граница для произвольного Unicode; перед отправкой нужен расчёт **реально собранного** payload каждой стадии. Каждая часть повторно передаёт полный черновик, поэтому количество частей и длина ответов влияют на общую цену. Без успешного полного запуска v3 экономия или укладывание в $0.10 не доказаны.

До terminal полный резерв остаётся занятым. После terminal фактическое списание берётся из Batch `usage.cost`; если оно отсутствует либо `usage.is_byok=true`, резерв остаётся занятым: при BYOK OpenRouter сообщает только комиссию шлюза, а inference оплачивается отдельно у провайдера. Явный provider cache не создаётся, а скидка от возможного hit заранее не вычитается: [руководство по Gemini caching](https://openrouter.ai/docs/guides/best-practices/prompt-caching) само по себе не подтверждает hit для сочетания 3.7 Flash, Batch и выбранного endpoint. В metadata прежнего реального smoke OpenRouter назвал закреплённую ревизию `google/gemini-3.7-flash-20260813`, тогда как Chat body сохранил alias `google/gemini-3.7-flash:batch`; валидатор принимает только эти два точных имени при совпадающих Batch ID, endpoint и `custom_id`.

## Граница и единый публикуемый документ

Вход — готовый `transcript.json` и его существующие speaker/time metadata. [`source.py`](../summary/luna_v1/source.py) сериализует реплики канонически с U ID, говорящим и временем; word-level данные и аудио наружу не отправляются. [`prompt_v1.md`](../summary/luna_v1/prompt_v1.md) — самостоятельная инструкция для Luna, [`output_schema_v1.json`](../summary/luna_v1/output_schema_v1.json) — версия одного типизированного документа. Вызов запрашивает восемь разделов, хронологию, опоры на исходные реплики и содержательные карточки. Предложение, отрицание, альтернативу, условие и неизвестные поля он должен передавать честно. Неизвестные исполнитель и срок не мешают созданию конкретной локальной задачи. Это контракт, а не доказательство фактической точности модели.

Новый маршрут планирует **3–4 генерации без повторной проверки, 4–5 при наличии безопасных патчей**: один Luna writer, две или три последовательные проверки частей Gemini и условный адресный `verify`. Фактическое число может быть меньше при заблокированной стадии; неисполненную часть нельзя считать проверенной. Повторного ASR, Plane и неограниченного repair-цикла нет:

1. `summary`: [`prompt_v1.md`](../summary/luna_v1/prompt_v1.md) и схема v1 дают полный черновой документ. Raw, usage, исходный SHA и документ сохраняются до quality-стадий.
2. `segment_1`–`segment_2` или `segment_3`: каждый Gemini item получает свою primary-часть стенограммы, пограничный контекст, полный закреплённый черновик и список относящихся к части элементов. Сразу возвращаются source items с оценкой в той же строке, только проблемные или неопределённые оценки элементов черновика, находки и допустимые правки целых элементов. Пропущенные элементы черновика остаются `unassessed`, а не получают молчаливый PASS. Перед отправкой следующей части известный полный счёт завершённой заменяет её резерв; неизвестное списание оставляет резерв занятым. Host объединяет результаты относительно исходного черновика и удерживает конфликтующие патчи.
3. `verify` вызывается **только при применённых патчах из проверок частей**. Gemini получает адресный источник, связанные пункты, исправленный черновик и прежние находки. Если последняя проверка вносит ещё один патч, он локально валидируется, а статус `postverify_corrected_unchecked` сообщает, что его смысл повторно моделью не проверялся. Следующей безусловной волны нет.

Публикация не отменяется из-за оставшейся смысловой неопределённости: она показывается в документе и `quality_review`. Если часть не удалось отправить или завершить либо отчёты не удалось объединить, статус `segment_review_unavailable` указывает неполную проверку; безопасные патчи из завершённого префикса могут быть применены после локальной проверки. При недоступной последней проверке исправленного результата ставится `verify_unavailable`. Несогласованные строки покрытия дают `coverage_incomplete`, не ложное «всё проверено». Непарсируемый или структурно непригодный документ нельзя безопасно отрисовать: его raw и точная ошибка сохраняются, а прежняя generation остаётся доступной. Проверки JSON, source IDs и согласованности полей не доказывают, что реплики действительно подтверждают каждый тезис или что обе модели нашли все пропуски. Даже статус `model_segment_reviewed_checked` не гарантирует смысловую полноту всей встречи. [`render.py`](../summary/luna_v1/render.py) строит Markdown, HTML, JSON, локальный task export и навигацию из одного принятого документа и effective task state. Модельные версии хранятся отдельно от ручных правок; [`tasks.py`](../summary/luna_v1/tasks.py) использует стабильные action IDs и optimistic revision.

Новая generation имеет `contract_version: luna_summary_v1` и отдельный набор файлов; [`publication.py`](../summary/luna_v1/publication.py) готовит candidate, проверяет исходный SHA и публикует `summary_current.json` последним под lock. Ошибка до смены pointer оставляет предыдущий принятый результат. Старые поколения должны читаться по их прежнему контракту, без поддельных MeetingGraph/audit PASS-файлов. Интеграция reader dispatch и штатной очереди с этим контрактом — отдельная проверяемая часть rollout, не свойство одной лишь библиотеки.

## Внешний маршрут и приватность

Пользователь разрешил для writer и judge **OpenRouter Batch с хранением входа и результата у OpenRouter до 30 дней и без запроса provider ZDR**. Это не сквозной режим нулевого хранения. Текущая карточка [Luna Batch](https://openrouter.ai/openai/gpt-6-luna:batch) показывает first-party OpenAI как доступного writer-провайдера; [OpenRouter ZDR](https://openrouter.ai/docs/guides/features/zdr) исключает этот endpoint при включённом OpenAI ZDR. Judge закреплён за Google Vertex через `provider.only`; [список провайдеров OpenRouter](https://openrouter.ai/providers/) обозначает Google Vertex как no training/zero retention upstream, но это не отменяет хранения Batch-артефактов у OpenRouter. Согласие пользователя не снимает account/guardrail policy и не доказывает права конкретного ключа на маршрут. Каждый маршрут проверяется перед платной отправкой по metadata ключа, доступному каталогу, модели и endpoint; BYOK не приравнивается к ZDR.

По [Batch API Quickstart](https://openrouter.ai/docs/batch-quickstart) OpenRouter сохраняет Batch JSONL в своём Google Cloud Storage и удаляет через 30 дней; upstream retention зависит от провайдера. `DELETE` после terminal удаляет артефакты OpenRouter раньше и возвращает отдельный upstream status; для Google Vertex заявлена поддержка upstream deletion. Это не меняет факт первоначальной обработки и хранения. Код не запрашивает web/tools/plugins и gateway response cache. Для сохранённой Gemini policy необязательные account opt-ins для private input/output logging и использования данных должны быть выключены до нового приватного dispatch. При текущей Opus policy с I/O logging ON код блокирует новые writer и judge POST старой Gemini policy с требованием OFF; уже отправленные Batch продолжают опрашиваться по своим remote ID. Для возобновления новых Gemini writer и judge стадий нужен совместимый runtime со старой Gemini policy и проверенный I/O logging OFF для соответствующих ключей и workspace. Метаданные ключа и модельный каталог **не подтверждают** состояние этих настроек. [Data Collection](https://openrouter.ai/docs/guides/privacy/data-collection) различает такие opt-ins; [response caching](https://openrouter.ai/docs/guides/features/response-caching) — отдельное хранение ответа и здесь не запрашивается.

Writer и отдельный judge client используют OpenRouter `POST /api/v1/batches` с одним item на стадию; judge передаёт модель `google/gemini-3.7-flash:batch` и закрепляет `google-vertex`. Исторические уже отправленные quality jobs дочитываются с сохранённым route; новый Gemini POST блокируется текущей Opus policy. Три–пять оплачиваемых генераций нового маршрута являются отдельными Batch item; части начинаются последовательно после terminal и учёта фактического счёта либо сохранённого резерва предыдущей. Scheduler сохраняет terminal status, raw, usage и ошибки каждой стадии, затем удаляет только **свой** terminal Batch. Ошибка/неизвестный исход POST остаётся в ledger; новый POST другим ключом автоматически не выполняется. `verify` не отправляется до применения патчей. Видимость чужих batches в том же workspace не даёт приложению права их читать или удалять.

## Ключи, кэш и деньги

Администратор вводит OpenRouter inference-ключи для writer и judge через защищённый `/summary-settings`; браузер не вызывает OpenRouter с ключом или стенограммой. [`summary_credentials.py`](../scripts/summary_credentials.py) хранит зашифрованные токены в приватном SQLite через Fernet, с master key отдельно; GET возвращает label/маску и metadata. У ролей отдельные основной ключ и резервы, но общий денежный ledger. Для новых отправок берётся актуальная версия ключа своей роли; отключение запрещает новые отправки, но позволяет дочитать уже отправленный job. Замена/удаление при незавершённом job закрывается. Подробные настройки runtime, Origin, admin verifier и тесты — в [`SUMMARY_ADMIN_KEYS.md`](SUMMARY_ADMIN_KEYS.md). Проверка ключа через `GET /api/v1/key` бесплатна и не проверяет Batch/model/privacy целиком.

Локальный semantic cache и single-flight в [`ledger.py`](../summary/luna_v1/ledger.py) основаны на SHA исходника и его канонической проекции, workspace scope, версиях writer и quality prompts/schemas, политики, параметров сегментации, модели, privacy mode, reasoning/output caps. Секретная строка ключа в cache identity не входит. Если уже существует принятый идентичный **итоговый** результат, он может быть повторно использован без новых генераций; бюджет нового запуска рассчитывается без предположения такого hit. Pending `summary`, `segment_1`–`segment_3` и `verify` после restart продолжаются по сохранённым identity и remote ID, а не отправляются заново. Запрос и target для каждого stage сохраняются до manifest, разрешающего POST, с проверкой на рестарте. Ответ с ошибкой или незавершённая цепочка не являются accepted cache hit. Provider prompt cache не запрашивается принудительно, hit и экономию можно признавать лишь по фактическому usage. Gateway response cache не включён.

Общий ledger ограничивает все ключи и workers **$1.00 за скользящие семь суток**, обычную логическую пересборку **$0.10** и не более **6** потенциально оплачиваемых dispatch. Для одного явно названного terminal failed writer пользователь разрешил динамический предел продолжения: отдельная запись авторизации снимает только фиксированный суммарный предел $0.10 для его billing group. Каждая физическая отправка по-прежнему ограничена $0.10, перед ней транзакционно проверяется свободный остаток общего недельного $1 и общий счётчик шести вызовов. Это не переносится на другие встречи, группы или ключи. Плановая цепочка нового контракта занимает **3–5 генераций**: writer, две или три проверки частей и условный `verify`; при продолжении от сохранённого writer новая генерация Luna не нужна, но её прежнее списание остаётся в той же группе. Перед **каждым** POST резервируется верхняя оценка без обещанного cache hit: лимит вывода writer — `32000`, Gemini packed segment review — `7500` на часть, verify — `3000` токенов. После terminal OpenRouter Batch `usage.cost` заменяет резерв при наличии полного, известного счёта; неизвестное списание оставляет резерв занятым. Следующая часть резервируется только после этого учёта предыдущей. Если новая стадия не помещается в применимый бюджет, она не отправляется, а пригодный кандидат публикуется с явным ограничением проверки. Несколько ключей не увеличивают лимит; каждый Batch item, повтор и неизвестная отправка учитываются как потенциальная платная генерация. Отсутствие тарифа, ключа или бюджета блокирует новую стадию, но не ASR и не чтение уже принятого конспекта.

Перед приватным POST оператор проверяет настройки **каждого используемого workspace**, включая BYOK, I/O logging и фильтры Included/Excluded API Keys, data discount и обучение на платных запросах. Для нового Opus job ожидается I/O logging ON у writer и judge; для сохранённых Gemini jobs действует их прежняя policy. Inference-key `GET /key` не раскрывает эти настройки, а Batch `provider.only` не исключает BYOK. Для writer `TRANSCRI_SUMMARY_VERIFIED_WORKSPACE_ID` задаётся в защищённой конфигурации только после такой проверки; worker сопоставляет его с `workspace_id` writer-ключа и иначе возвращает `account_policy_unverified_for_workspace` до POST. Judge workspace закрепляется в root manifest при writer dispatch и повторно сверяется с judge-ключом и живым route перед стадией; отдельного автоматического attestation gate для его account policy нет. Проверку оператора нужно повторить при изменении workspace policy. Для резерва используются максимальные опубликованные ставки также из `pricing.overrides` и консервативная цена возможной записи кэша; фактическая стоимость после Batch может быть ниже.

## Установка, восстановление и откат

Для нового HTTP/credential worker предусмотрен отдельный summary Python runtime; speech venv, CUDA/Torch, FFmpeg, VAD, ASR, диаризация, voice profiles и upstream transcript остаются неизменными. Admin endpoint остаётся на loopback за проверенной административной защитой и безопасным каналом; настройки master key, verifier и isolated runtime приведены в [`SUMMARY_ADMIN_KEYS.md`](SUMMARY_ADMIN_KEYS.md). Прямой публичный доступ к dashboard не является допустимым способом настройки.

Linux-проверка 2026-09-26 зафиксировала отдельный изолированный Luna release и работающие summary dashboard/scheduler после обновления кандидата. В ходе переключения одна попытка запуска этих двух служб не прошла из-за отсутствующей ссылки на `config.json`; после адресного восстановления конфигурации обе службы запустились, а speech service продолжал работать. Это не подтверждает включение нового backend в речевой production pipeline. Перед следующим rollout повторно устанавливают фактические service/release/worktree и pending jobs через Linux-доступ; уже отправленные Batch восстанавливают по сохранённому remote ID, не создавая дубликат. Ни ключи, ни raw частной встречи, ни job ID не входят в публичный репозиторий. При отказе останавливают только изолированные Luna-службы и убирают их маршрут; речевой release продолжает работу.

Текущий проверенный снимок `pipeline.py` сохраняет прежний SHA в ключах кэша речевых стадий, хотя добавлена только summary-интеграция. Проверка точного SHA самого миграционного файла защищает это исключение: любое последующее изменение `pipeline.py` автоматически возвращает фактический SHA и может вызвать пересчёт речевого кэша при полном retry. Перед следующим изменением файла отдельно проверьте его влияние на защищённые стадии и обновите миграционный снимок только после ревью. Summary-only повтор не проходит через речевые стадии.

Удаление записей в действующем production проверено для terminal legacy jobs. `record_dashboard_wrapper.py` намеренно возвращает HTTP 409 при связи output с `state/summary_private/luna.sqlite3`, включая accepted Batch: локальный ledger, raw и ручные карточки остаются для аудита. Поэтому общий Luna+delete в `main` пока не гарантирует удаление Luna-записи, даже если кнопка показана. До совмещённого rollout нужен отдельный протокол terminal-only detach с сохранением billing audit, очисткой приватных payload и проверкой restart/cache/shared consumer; действующее удаление legacy-записей не меняется.

При rollout сначала проверяют изолированный release, актуальную source revision, prompt/schema/quality-policy hashes и все начатые jobs. Для каждого `summary`, `segment_1`–`segment_3`, `verify` приватный каталог хранит manifest, request без токена, submit response/error, terminal Batch, точный raw/usage и результат локальной обработки; корневой job дополнительно хранит план частей, отчёты по завершённым частям, draft, revised/final candidate и `quality_decision.json`. Старые `inventory_*`/`reconcile` каталоги относятся к закреплённым legacy jobs. `quality_review` входит в sealed generation и виден в Markdown/HTML/JSON. Использованный для последней стадии credential ID/version сохраняется без самого ключа. При `submission_unknown` новый POST запрещён до выяснения исхода; при restart scheduler продолжает по ledger и remote ID. Публикация собирает candidate отдельно и переключает `summary_current.json` последним, сохраняя предыдущую generation до успешного commit.

Для исторической попытки ранней Luna v3 с прежним ошибочным валидатором есть узкое offline-восстановление `scripts/recover_luna_summary_v3.py`: оно сверяет SHA исходника, manifest, writer draft, audit report и исполняемого кода, применяет уже оплаченный audit и публикует отдельную generation без нового HTTP-запроса. Оно не относится к новой сегментной policy v3 packed. `--apply` должен запускать владелец приватного summary state, то есть штатный пользователь worker; инструмент проверяет UID до записи, чтобы закрытые файлы не стали недоступными ему. Исходные raw/failed candidate/ошибка остаются; исходный `quality_decision.json` копируется в неизменяемое свидетельство перед заменой sidecar на статус `audit_recovered_unverified`. Отсутствовавший verify не объявляется выполненным. Указатель проверяется повторно под publication lock, а переход ledger выполняется условно и идемпотентно. Это восстановление конкретного failed job, не общее разрешение считать структурную проверку смысловой приёмкой.

После приёмки включают `summary_backend: luna_batch` только для summary-only очереди. Откат возвращает прежний release/backend и reader, не удаляя transcript, sealed generations, ручные правки, частные raw и billing ledger; он не запускает старую модель скрытым fallback для неудачной стадии. Отмена новой стадии не отзывает автоматически уже принятую внешним Batch отправку; её состояние и возможная стоимость остаются в ledger. Общий watcher перезапускают только в безопасное окно, не прерывая обработку речи.

Перед платным приёмочным запуском новой версии проверяют собранный payload без секрета, размер входа и бюджет ожидаемых стадий, актуальный ledger и отсутствие незавершённого прежнего job для того же источника. Для зависимой стадии окончательный payload и резерв рассчитываются после появления её входного результата; если лимит не позволяет dispatch, это сохраняется как ограничение, а не обходится новым ключом. После terminal читают raw/status/usage **каждой фактически исполненной стадии** и итоговый полный конспект по исходной стенограмме, включая задачи, роли, условия, альтернативы, числа и поздние поправки. Сохранённый `quality_review` сообщает об охвате автоматической процедуры, а не удостоверяет отсутствие смысловых ошибок. Stub/unit-тесты и прежние полные результаты других политик не заменяют приёмку новой.
