# Управление ключами OpenRouter для суммаризатора

Эта функция относится только к summary-only backend. Она не меняет ASR/диаризацию и не подключает Plane. Ключи добавляют в `/summary-settings`; браузер не отправляет стенограмму в OpenRouter. Проверка ключа выполняет только бесплатный `GET /api/v1/key` с Linux backend и подтверждает аутентификацию/доступные поля лимита, но не право на `openai/gpt-6-luna`, ZDR или Batch.

## Защищённый запуск

1. В **отдельном summary runtime** установите `requirements-summary-credentials.txt` (`cryptography` для Fernet и `pydantic` для изолированного dashboard) и задайте `TRANSCRI_SUMMARY_PYTHON` как абсолютный путь к его Python. Не обновляйте `.venv-core` или ASR/diarization venv. Dashboard выполняет одноразовый защищённый helper в этом runtime; JSON с вводимым ключом передаётся только по stdin, не через argv, URL, env или журнал. Helper возвращает лишь маску и metadata. При отсутствующем runtime admin-операции закрыты; процесс обработки речи продолжает работать.
2. Передайте Fernet master key через `TRANSCRI_SUMMARY_MASTER_KEY_FILE`: абсолютный путь к обычному файлу владельца процесса с правами `0600`, в отдельном защищённом серверном хранилище. Приложение хранит SQLite только в `state/summary_private/credentials.sqlite3` (каталог `0700`, файл `0600`), а master key не кладёт в эту папку, Git, публичный config или архив. Альтернативный `TRANSCRI_SUMMARY_MASTER_KEY` в защищённом окружении допустим для bootstrap и тестов; задайте ровно один источник. Не теряйте master key: без него сохранённые inference-ключи не открыть.
3. Задайте `TRANSCRI_SUMMARY_ADMIN_PASSWORD_HASH` как scrypt verifier. Его можно создать в доверенной консоли без аргумента с паролем и без передачи пароля в shell history: `python3 -c 'import getpass,sys;sys.path.insert(0,"scripts");from summary_credentials import make_admin_password_hash;print(make_admin_password_hash(getpass.getpass("Admin password: ")))'`. Используйте пароль не короче 16 символов и сохраните только хеш в защищённой настройке сервиса. Это отдельная административная защита, а не OpenRouter Management key.
4. Проверка Linux 2026-09-25 подтвердила существующий Tailscale Serve: HTTPS `:8443` проксирует действующий dashboard `127.0.0.1:8765`. Изолированный dashboard теперь слушает `127.0.0.1:8766` и доступен через отдельный tailnet HTTPS `:8444`; исходные маршруты `:443` и `:8443` сохранены. Точный HTTPS Origin задан в закрытой настройке службы, а не в репозитории. Это защищённый транспорт, а не замена административной авторизации: сервер проверяет loopback peer, точный Host, Basic admin credential, для записи также Origin, `X-Requested-With` и `Sec-Fetch-Site`; proxy identity headers не принимаются за авторизацию. Без verifier endpoints закрыты (`503`). Прямой порт dashboard не публикуйте в интернет. Проверка реального endpoint дала 401 без администратора, 200 с ним и 403 для неверного Origin. Позднее реальный inference-ключ проверили через защищённый UI, а синтетический Batch smoke завершился; открытый ключ и его metadata не публикуются. Эти проверки не подтверждают, что действующий production release переключён на Luna.

Новые защищённые маршруты: `GET /summary-settings`, `GET /summary-settings.js`, `GET /api/summary/credentials`; `POST /api/summary/credentials/{add,check,replace,order,enabled,delete}` с JSON не более 4096 байт. GET/ответы не содержат открытого inference-ключа. UI держит введённый ключ лишь до отправки формы и очищает поле. В SQLite ключ хранится как Fernet ciphertext, а изменения журналируются как операция/credential ID/version/actor без токена.

## Ротация и незавершённые jobs

Порядок ключей определяет один основной и явные резервы; несколько ключей не увеличивают общий денежный лимит. Проверка `GET /api/v1/key` может показать workspace ID и лимит конкретного ключа, но не считайте совпадение label доказательством общего workspace. Worker должен читать кандидатов заново через `CredentialStore.dispatch_candidates()` перед каждой новой отправкой. Затем **сначала** создать durable ledger reservation с ID/version, **потом** открыть конкретный секрет через `reveal_for_dispatch(id,version)` непосредственно перед POST. При несовпадении версии нельзя отправлять запрос по старой reservation.

`enabled=false` запрещает новые отправки, но не удаляет secret: `reveal_for_existing_job(id,version)` позволяет получить уже отправленный Batch job. Замена и локальное удаление блокируются, пока `Ledger.active_summary_jobs_for_credential(id)` считает незавершённые запросы; при ошибке ledger операция закрыта. После drain можно заменить/удалить. Локальное удаление **не отзывает** ключ у OpenRouter; отзыв выполняется отдельно в кабинете провайдера. Если внешняя отправка неизвестна, её следует восстановить по ledger, а не повторять другим ключом.

## Batch и приватность

Пользователь отдельно разрешил для выбранного Luna/OpenRouter Batch хранение входа/результата у шлюза до 30 дней и Batch **без** `provider.zdr`. Это именно разрешённый режим Batch, не сквозной ZDR. Раннее удаление после terminal не меняет факт первоначального хранения. Необязательные private I/O logs, использование данных ради скидки, плагины, web search и training остаются выключенными. Публичный контракт и первоисточники приведены в [SUMMARY_LUNA_BATCH.md](SUMMARY_LUNA_BATCH.md); реальное право ключа на модель, route, бюджет и account policies проверяются перед отправкой частной встречи.

## Проверка

`python3 -m unittest tests.test_summary_credentials_admin -v` в тестовом runtime с `cryptography` проверяет реальные handler methods без сетевого listener и через одноразовый helper: шифрованное хранение, отсутствие секрета в API, Origin/Host/auth защиту, версию, disable/poll и запрет удаления активного ключа на фиктивных данных. Это не live-проверка ключа или deployment.
