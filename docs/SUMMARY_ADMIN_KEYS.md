# Управление ключами OpenRouter для суммаризатора

Эта функция относится только к summary-only backend. Она не меняет ASR/диаризацию и не подключает Plane. Ключи добавляют в `/summary-settings`; браузер не отправляет стенограмму провайдерам. Автор конспекта использует OpenRouter/Luna; проверяющий и ограниченный repair используют отдельно выбранные ключи OpenRouter для `google/gemini-3.7-flash:batch` с закреплённым Google Vertex. Бесплатная проверка обоих ролей выполняет с Linux backend `GET https://openrouter.ai/api/v1/key`. Она возвращает metadata ключа, включая workspace и доступный лимит, но не подтверждает право на конкретную модель, Batch, тариф или все настройки приватности; маршрут проверяется отдельно до платного POST. [Контракт проверки ключа](https://openrouter.ai/docs/api/api-reference/api-keys/get-current-api-key).

## Защищённый запуск

1. В **отдельном summary runtime** установите `requirements-summary-credentials.txt` (`cryptography` для Fernet и `pydantic` для изолированного dashboard) и задайте `TRANSCRI_SUMMARY_PYTHON` как абсолютный путь к его Python. Не обновляйте `.venv-core` или ASR/diarization venv. Dashboard выполняет одноразовый защищённый helper в этом runtime; JSON с вводимым ключом передаётся только по stdin, не через argv, URL, env или журнал. Helper возвращает лишь маску и metadata. При отсутствующем runtime admin-операции закрыты; процесс обработки речи продолжает работать.
2. Передайте Fernet master key через `TRANSCRI_SUMMARY_MASTER_KEY_FILE`: абсолютный путь к обычному файлу владельца процесса с правами `0600`, в отдельном защищённом серверном хранилище. Приложение хранит SQLite только в `state/summary_private/credentials.sqlite3` (каталог `0700`, файл `0600`), а master key не кладёт в эту папку, Git, публичный config или архив. Альтернативный `TRANSCRI_SUMMARY_MASTER_KEY` в защищённом окружении допустим для bootstrap и тестов; задайте ровно один источник. Не теряйте master key: без него сохранённые inference-ключи не открыть.
3. Задайте `TRANSCRI_SUMMARY_ADMIN_PASSWORD_HASH` как scrypt verifier. Его можно создать в доверенной консоли без аргумента с паролем и без передачи пароля в shell history: `python3 -c 'import getpass,sys;sys.path.insert(0,"scripts");from summary_credentials import make_admin_password_hash;print(make_admin_password_hash(getpass.getpass("Admin password: ")))'`. Используйте пароль не короче 16 символов и сохраните только хеш в защищённой настройке сервиса. Это отдельная административная защита, а не OpenRouter Management key.
4. Проверка Linux 2026-09-25 подтвердила существующий Tailscale Serve: HTTPS `:8443` проксирует действующий dashboard `127.0.0.1:8765`. Изолированный dashboard теперь слушает `127.0.0.1:8766` и доступен через отдельный tailnet HTTPS `:8444`; исходные маршруты `:443` и `:8443` сохранены. Точный HTTPS Origin задан в закрытой настройке службы, а не в репозитории. Это защищённый транспорт, а не замена административной авторизации: сервер проверяет loopback peer, точный Host, Basic admin credential, для записи также Origin, `X-Requested-With` и `Sec-Fetch-Site`; proxy identity headers не принимаются за авторизацию. Без verifier endpoints закрыты (`503`). Прямой порт dashboard не публикуйте в интернет. Проверка реального endpoint дала 401 без администратора, 200 с ним и 403 для неверного Origin. Позднее реальный inference-ключ проверили через защищённый UI, а синтетический Batch smoke завершился; открытый ключ и его metadata не публикуются. Эти проверки не подтверждают, что действующий production release переключён на Luna.

Защищённые маршруты: `GET /summary-settings`, `GET /summary-settings.js`, `GET /api/summary/credentials`; `POST /api/summary/credentials/{add,check,replace,order,enabled,delete}` с JSON не более 4096 байт. Старое подтверждение «оплачиваемого Google-проекта» к ключам OpenRouter неприменимо; форма и gate отправки удалены. Ранее сохранённый judge-ключ можно повторно проверить кнопкой «Проверить» без замены секрета. GET/ответы не содержат открытого inference-ключа. UI держит введённый ключ лишь до отправки формы и очищает поле. В SQLite ключ хранится как Fernet ciphertext, а изменения журналируются как операция/credential ID/version/actor без токена. Ранее сохранённые OpenRouter-ключи остаются writer-ключами с прежними ID/версиями; миграция не расшифровывает их. Устаревшие колонки Google-attestation в существующей SQLite сохраняются для аддитивной миграции, но больше не читаются как право на отправку.

## Ротация и незавершённые jobs

Порядок ключей каждой роли определяет один основной и явные резервы; несколько ключей не увеличивают общий денежный лимит. Проверка `GET /api/v1/key` может показать workspace ID и лимит конкретного ключа, но не считайте совпадение label доказательством общего workspace. Worker должен читать кандидатов заново через `CredentialStore.dispatch_candidates(role=...)` перед каждой новой отправкой. Для бесплатного preflight он открывает выбранный секрет, затем создаёт durable ledger reservation с ID/version и **повторно** открывает ту же версию через `reveal_for_dispatch(id,version)` непосредственно перед POST. При несовпадении версии нельзя отправлять запрос по старой reservation. Judge workspace закрепляется в manifest при writer dispatch и повторно проверяется перед `audit`/`verify`.

`enabled=false` запрещает новые отправки, но не удаляет secret: `reveal_for_existing_job(id,version)` позволяет получить уже отправленный Batch job. Замена и локальное удаление блокируются, пока `Ledger.active_summary_jobs_for_credential(id)` считает незавершённые запросы; при ошибке ledger операция закрыта. После drain можно заменить/удалить. Локальное удаление **не отзывает** ключ у OpenRouter; отзыв выполняется отдельно в кабинете провайдера. Если внешняя отправка неизвестна, её следует восстановить по ledger, а не повторять другим ключом. Проверка judge-ключа использует тот же OpenRouter metadata endpoint, что и writer, но роли, порядок основных/резервных ключей и доступ к секретам остаются раздельными. Денежный ledger общий. Смена секрета требует новой проверки.

## Batch и приватность

Пользователь разрешил для writer и judge OpenRouter Batch с хранением входа/результата у шлюза до 30 дней и Batch **без** запроса `provider.zdr`. Это разрешённый режим Batch, не сквозной ZDR. Раннее удаление после terminal не меняет факт первоначального хранения. Перед частным запуском оператор проверяет настройки используемых workspace: необязательные private I/O logs, использование данных ради скидки и обучение на платных запросах должны быть выключены; код не запрашивает плагины и web search. `GET /api/v1/key` не доказывает состояние этих настроек. Публичный контракт и первоисточники приведены в [SUMMARY_LUNA_BATCH.md](SUMMARY_LUNA_BATCH.md).

Judge отправляет текст через OpenRouter Batch `POST /api/v1/batches` с `provider.only: ["google-vertex"]`; недоступный Google Vertex endpoint блокирует эту стадию без автоматического перехода к другому провайдеру. Перед POST проверяются фактическая модель/endpoint, workspace, ключевой и общий лимиты, текущий тариф и контекстный предел. Подтверждение Google project или paid tier здесь не требуется: judge-ключ является OpenRouter inference-ключом. [Официальный Batch-контракт](https://openrouter.ai/docs/batch-quickstart) описывает хранение шлюза и terminal deletion; [список провайдеров](https://openrouter.ai/providers/) отдельно описывает upstream Google Vertex. Открытый ключ в чате не нужен. Кэш результата локальный; явный provider cache не создаётся и скидка от возможного hit заранее не учитывается.

## Проверка

`python3 -m unittest tests.test_summary_credentials_admin -v` в тестовом runtime с `cryptography` проверяет реальные handler methods без сетевого listener и через одноразовый helper: шифрованное хранение, отсутствие секрета в API, Origin/Host/auth защиту, версию, disable/poll и запрет удаления активного ключа на фиктивных данных. Это не live-проверка ключа или deployment.
